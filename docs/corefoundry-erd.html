CoreFoundry · data model · v1

Two kinds of database, one MySQL server

corefoundry stores what users designed: accounts, projects, members, draft tables and columns, and the history of every schema change. Each project also gets its own cf_p_<id> database, which holds the real tables built from that design. The requests that read and write these tables are drawn in backend flows.

Metadata database

corefoundry: entity relationships

Seven tables, managed by EF Core migrations. The dashed copper link is the only connection to a project database. The database name is derived from Projects.Id (cf_p_{Id}) rather than stored, and it isn't a foreign key, because MySQL can't enforce keys across databases here.

Users

  • Email is lower-cased before it's saved, and unique.
  • PasswordHash uses ASP.NET Core PasswordHasher (PBKDF2).

RefreshTokens

  • Only the SHA-256 hash is stored, never the raw token.
  • Each refresh revokes the old row and links it to the new one.
  • If a revoked token is used again, every token in its chain is revoked.

Projects

  • The database name cf_p_{Id} is computed from the Id, never stored and never user input.
  • SchemaVersion goes up by one on every successful apply.
  • Status: Provisioning · Active · Failed · Deleting.

ProjectMembers

  • Composite PK (ProjectId, UserId); index on UserId for "my projects".
  • Exactly one Owner row per project, matching Projects.OwnerId. Update both in one transaction.

ProjectTables

  • UQ (ProjectId, Name).
  • AppliedName null means the table was never created.
  • PendingDrop marks a delete that waits for the next apply.

ProjectColumns

  • UQ (TableId, Name). The stable Id is what makes rename detection work.
  • Length, Precision and Scale are checked against DataType.
  • DefaultValue is stored as text and written into SQL as a typed literal.

SchemaMigrations

  • Journal of every apply. UQ (ProjectId, Version).
  • StatementsApplied of StatementCount shows how far a failed apply got.
  • SnapshotJson is the applied schema. The Data API reads it, never the draft.
Physical layout

Where the generated tables live

One MySQL 8.4 server, two login accounts. The metadata code and the schema engine connect as different users, so a bug in the engine can't touch the metadata.

Worked example · project “Bookshop”, id 7

How a draft becomes a real table

The draft is compared with what INFORMATION_SCHEMA reports for cf_p_7.books. Each column's Name and AppliedName are enough to classify the change.

Generated databases

Rules every cf_p_<id> database follows

System primary key

Every table starts with `id` BIGINT AUTO_INCREMENT PRIMARY KEY. It's not in the metadata and can't be edited, and the Data API uses it to identify rows.

Names come from metadata

Table and column names are the validated Name (^[a-z][a-z0-9_]{0,62}$, not a reserved word) and are always wrapped in backticks.

Engine and charset

ENGINE=InnoDB, utf8mb4 / utf8mb4_0900_ai_ci for every database and table.

Unique keys

Named uq_<table>_<column> so the differ can find and drop them by name.

No foreign keys (v1)

Relationships between generated tables are planned for later. Without them, the order of drops and type changes doesn't matter.

Column order

OrdinalPosition only controls display order. The engine doesn't physically reorder columns, which would rebuild the table for no benefit.

Integrity
