What happens between a click and a CREATE TABLE

This page follows every request in CoreFoundry through its layers, checks and SQL: signing in, authorization, project setup, the schema engine, and the Data API. The tables and columns referenced here are defined in the data model.

Architecture

Four layers, dependencies point inward

The Domain layer does no I/O, so the most dangerous logic (diffing a schema and deciding what to drop) can be tested with plain unit tests. Infrastructure implements interfaces defined by Application and is wired in by the Api layer at startup.

App flow

The user journey, screen by screen

Six screens, each backed by a small set of endpoints. Nothing touches the project's real database until someone presses Apply.

Authentication

Sign-in, refresh rotation and replay detection

The access token lasts 15 minutes and is kept in memory, never in localStorage. The refresh token is in an httpOnly cookie, and only its hash is stored in the database. Each refresh replaces the refresh token with a new one, so presenting an old token again is treated as theft.

Authorization

One check covers every project route

Every route starts with /api/projects/{projectId}, so one ProjectRoleRequirement handler reads ProjectMembers and decides. Each endpoint only declares the minimum role it needs.

Projects

Project lifecycle: metadata first, database second

A database can't be created inside the same transaction as the metadata, so Projects.Status records where the process has got to. POST /projects inserts the project with Provisioning status, plus its Owner member row, in one EF transaction. After that it runs CREATE DATABASE.

Schema engine · part 1

Plan: compare the draft with reality

GET …/schema/plan turns both sides into the same SchemaModel shape and compares them. It reads the real schema from INFORMATION_SCHEMA, not from the last snapshot, so anything a failed apply left behind is picked up automatically.

Rename or drop?

Name ≠ AppliedName on the same column Id is a rename. A column whose AppliedName is missing from the draft is a drop.

Destructive changes are flagged

Dropping a table or column, making a type narrower (e.g. VARCHAR(200)→(50)) and changing NULL→NOT NULL each add a warning that Review plan shows in red.

One statement per table

All changes to a table go into one ALTER TABLE. New tables get one CREATE TABLE with every column. Each statement then either succeeds completely or does nothing.

Schema engine · part 2

Apply: no transaction to rely on, so keep a journal

MySQL commits each DDL statement immediately, so a failed batch can't be rolled back. Instead, every statement is atomic on its own, and a SchemaMigrations row records exactly how far the apply got.

Data API

Reading and writing rows in generated tables

The Data API only accepts names that exist in the latest applied snapshot, never names from the draft or the request. Every value is sent as a query parameter. Table and column names can't be parameters, so each one is checked against the snapshot and then wrapped in backticks.

Writes

POST / PUT bodies are checked field by field against the snapshot. An unknown field, id in the body, or a value of the wrong type gets 400 ProblemDetails with one error per field. Inserts return the new row's LAST_INSERT_ID().

Constraint errors

MySQL error 1062 (duplicate key) becomes 409 naming the unique column, and 1048 (NULL in a NOT NULL column) becomes 400. Raw MySQL messages never reach the client.
